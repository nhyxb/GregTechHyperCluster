## 三、实现要点与坑位（供后续 0.2.1 参考）

1. **多方块 `fullModifyRecipe` 会遍历全部 parts 的 `modifyRecipe`**——`IMaintenanceMachine.modifyRecipe` 在 `enableMaintenance` 时 veto 任何「有问题」批次。**GTCEu 约定 `ALL_PROBLEMS = 0`（bitmask 中 1 = 已修复）**，新维护仓初始即 6 问题全在，玩家必须先修复 hatch 才能开跑（真实游戏同样如此）。GameTest 中对维护仓 `fixAllMaintenanceProblems()` 模拟该玩家操作；这是塔类多方块配方「成型但永远 IDLE」的第一嫌疑位。
2. **测试环境的 MWSD 异步成型不可依赖**：`MultiblockWorldSavedData` 的 executor（250ms 轮询 + `(offset+periodID)%4` 相位门）在 GameTestServer 中始终未推进（`error=UNINIT` 停留）；`DataWorkshopTests.ensureTowerFormed` 以「lock + checkPatternWithLock + setFlipped + onStructureFormed」在服务器线程内复刻 `asyncCheckPattern` 的成型段，与生产路径等价且确定。真实世界由 executor 每秒级自动完成，客户端冒烟不受影响。
3. **结构模板 NBT 坑**：vanilla 结构 `size` 必须是 **TAG_List[Int]**（hc_field 初版写成 TAG_Int_Array 导致 `Failed to load structure`），`entities` 空表必须是 `TAG_List[TAG_Compound]`。`hc_field.nbt` 已随仓库提交（13×9×13 基岩地板），后续加模板时可直接对照其二进制格式仿写。
4. **EV = V[4] = 2048 EU/t**：配方 prepareBuilder 用 `GTValues.V[EV]`；OC_NON_PERFECT 对 2048 机器不超频 2048 档配方（2× 超 2048 越限），数据清洗以 2048×200t 满速运行；镜像铟分离 600 EU/t（HV~EV 之间）单次超频 1200×25t。**配方可跑档位判定**：`getRecipeEUtTier ≤ getMaxOverclockTier`（机器 tier 由能源仓电压下取整），越档配方 modifier 直接 NULL（游戏表现为「成型但类似无电」），排障时先打印 `fullModifyRecipe` 结果。
5. **渲染态**：多方块控制器比单方块机多 `is_formed` 维度（8 状态），`workableCasingModel` 自动完整生成 `.json`；overlay 目录约定 `assets/<mod>/textures/block/machines/<path>/overlay_front(_active).png` 与单方块机一致，美术交付贴图按该路径零改动接入。
6. **0.2.1 恢复点**：黄金样本、微调刻录舱、红队测试舱未开工；`Public/README.md` 已含 0.2 贴图清单美术核对。若后续给塔加「输入日志不混类」等配方级约束，`DATA_SCRUBBING_RECIPES` 类型 `SetMaxIOSize(4,3,2,0)` 尚有槽位余量。
